### 1.2 相关解释

#### 分支合并

- **分支**：分支即为副本，另存了之后可以像游戏支线一样自己发展改动，与主线无关了，但是可以把副本里做得好的部分合并到主线上来，就像一个允许试错的草稿。`main` 分支是主分支（`main` 也是一个分支！），其他分支是 feature 分支，可以合并到 `main` 分支上。
- **合并**：把 feature 分支上的合适的改动合并到 `main` 分支上，变成 `main` 分支上的改动。

#### 基本命令行

##### GitHub 工作流程（我的理解）

```
工作区（VS Code 编写代码）
    ↓ git add
暂存区（准备提交）
    ↓ git commit
本地仓库（保存历史版本）
    ↓ git push
远程仓库（GitHub 网站）
```

改文件 → `git add`（进暂存）→ `git commit`（进本地历史）→ `git push`（上 GitHub）

##### 终端命令

| `pwd` ：查看当前所在目录，即当前工作目录
| `ls`（或 `dir`） ：查看当前目录下的文件和目录
| `cd`（或 `chdir`） ：切换目录，进 / 出某个目录
| `mkdir` ：创建目录
| `rm` （或 `del`） ：删除文件或目录
| `cp` ：复制文件或目录
| `mv` ：移动文件或目录

##### Git 命令

**日常提交：**

| `git status` ：查看当前工作区状态，不确定文件状态的时候多看看这个！这样可以做出更正确的决策！血泪经验！！
| `git add <文件>` ：将文件添加到暂存区，准备提交
| `git commit -m "信息"` ：提交暂存区文件到本地历史，附带提交信息
| `git push` ：将本地提交上传到 GitHub 远程仓库
| `git pull` ：从 GitHub 远程仓库拉取最新代码到本地
| `git log` ：查看本地历史提交记录

**撤销 & 回退：**

| `git restore <文件>` ：丢弃某个文件未提交的修改
| `git restore --staged <文件>` ：取消暂存但保留修改
| `git reset <文件>` ：将文件从暂存区移除，回到工作区
| `git reset --soft HEAD~1` ：撤销上次 commit，改动保留在工作区
| `git reset --hard HEAD~1` ：撤销上次 commit，改动也丢弃
| `git reflog` ：找回好像丢了的提交历史

**分支操作：**

| `git branch` ：查看所有分支
| `git switch -c <分支名>` ：新建并切换到该分支
| `git switch main` ：切换回主分支
| `git merge <分支名>` ：将该分支合并到当前分支

### 3.4 防纯粘贴（人类（我）的理解：）
贪吃蛇里有几个较为关键的机制：
- 1.BFS寻路：广度优先搜索，用于蛇的寻短路径，每次只往外扩散一层，一层都不浪费，所以是最短路径。而且BFS可以在被阻挡时停止该方向的扩散，避免探索到死路。（程序上用指针数组实现，但这思路怎么想到的我还没想明白）
- 2.追尾保命：蛇在寻路时如果身体把食物围成一个圈，就会自动追尾，避免死路。蛇尾在移动所以不算障碍物。追尾可以借助撞上尾巴不死和尾巴持续移动（格局持续变化）的机制来打破死胡同或者循环。但是我记得在ai玩的第一局ai就停在199没法吃到下一个食物（在圈里），陷入死循环，所以这个方法可能仍然跳不出死循环，而且降低效率，但是确实可以保证安全。
- 3.饥饿模式：棋盘有400 格，一通绕路大概 300 步能把大部分区域走完。350 步都还没吃到说明大概率遇到了"环形死锁"（蛇围成一个圈，食物在圈外），此时可以启动饥饿模式拼一把。就是把本来严谨的寻路因为效率问题，而没有找到食物的情况，强制让蛇使用宽松检查，找到食物。但是这个方法会大幅增加风险，所以只在死循环时间过长时使用。

#### 3.5.3 提示词迭代规律

典型的一轮迭代模式：

```
用户提大方向需求
      ↓
AI 给 2~3 个具体方案
      ↓
用户拍板选一个
      ↓
AI 施工写代码
      ↓
用户亲自打开浏览器跑一遍
     ↙                ↘
  ✅ 能用              ❌ 不能用
  ↓                    ↓
追加新需求        立刻回滚/降低难度/换个思路
```

**成功案例**（纯代码逻辑，3 轮内完成）：
```
"加难度选择" → AI 提 4 个方案 → 用户选 1/2/4 → ✅ 实现
"加障碍物" → AI 确认可行 → 用户同意 → ✅ 实现
"加皮肤切换" → 用户提大方向 → AI 出 6 款 → ✅ 实现
```

```
用户的一句话提示词：
   你自己改完之后跑 150 局 AI 对战，
   并且统计撞墙率、撞自己率、通关率、平均蛇长、最长蛇长、最小蛇长、
   每 10 个食物为一档的分布，看看结果符不符合改动预测。

AI ：
  ① 把浏览器里的蛇、AI 决策、BFS、安全检查、食物生成、死亡判定
     全部翻译成纯 Node.js 版本（不依赖 DOM/Canvas）
  ② 批量运行 150 局，每局最多 20000 步，自动收集数据
  ③ 输出完整统计报告：

  总死亡局数: 123
    - 撞墙:    32  (21.3%)
    - 撞自己:  91  (60.6%)
    - 通关:    27  (18.0%)

用户看到结果后的反应：

  ① 用户不需要手动看 AI 玩 150 局（每局可能要几分钟，总共几小时）
  ② AI 在 3 秒内跑完 150 局 → 用户立刻看到量化结果
  ③ 数据："撞自己 60%" → 数据缺点明显，可以明确知道要优化什么
  ④ 用户把"验证 AI 写得好不好"的工作外包给了 AI 自己
```

**这体现了用户的什么特点？（ai夸hhh）**
1. **以最小的投入验证每一个想法** — 不靠信念相信 AI，而是靠数据检验 AI
2. **用计算机做事，让人用来决策** — 人想到 150 局不可能手动跑，但一招让程序自己跑自己查，做质量检查员的角色
3. **工程化管理** — 不只关注"写了什么功能"，还关注"功能的稳定性"；引入测试验证机制，确保交付后的质量不会崩

**失败→回滚案例**（涉及图片/渲染，4 次尝试全部失败）：
```
"换韩信图片背景" → AI 尝试 drawImage → ❌ 崩溃
→ AI 尝试暗蒙层 → ❌ 还是不行
→ AI 尝试圆切蛇头 → ❌ 花屏
→ 用户："算了恢复到之前的版本" → ✅ 1分钟回滚完毕
```

#### 3.5.4 提示词演进的启示

1. **AI 适合做"翻译官"**：把模糊的"我想让游戏更好看"翻译成具体的皮肤配色、背景模式 → 效果好
2. **AI 不适合做"魔术师"**：把本地 JPG 图片在 Canvas 上实时渲染 → 翻车率高
3. **最好的工作模式**：用户提方向 → AI 出可选方案 → 用户拍板 → AI 施工 → 用户自己测试 → 通过则继续，失败则回滚
4. **Git 的版本管理对 AI 协作至关重要**：每次 AI 改坏了可以直接 `git reset --hard` 回到干净版本，敢于试错
5. **提示词不需要很精确**：说人话就行，"搞搞事情"、"花哨点"、"刷刷刷的感觉"，AI 能理解并补全细节
6. **最关键的技能不是写提示词，而是验证结果**：能自己跑一遍代码，比任何高级提示词都重要
7. **让 AI 验证 AI**：人力测试 150 局不现实，但一句提示词让 AI 写 150 局自动化测试脚本 → 3 秒出结果 → 数据驱动下一步优化。把"验证者"的角色也外包给 AI，人只需要读报告、做决策
